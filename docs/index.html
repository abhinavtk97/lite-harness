Researching the agent-harness landscape

Before designing lite-harness, we surveyed 20+ existing AI coding-agent harnesses and orchestration frameworks to find out what they solve well, what they get wrong, and what nobody has built yet.

Status: research phase. No architecture decisions have been made yet. This page presents the problem statement, the requirements as understood so far, and the full landscape survey. Open questions that still need answers before the design phase starts are listed at the bottom.

Problem statement

We want to design and build an AI agent harness — the orchestration layer that runs an LLM agent loop, executes tools, enforces permissions, and manages session/context state.

The harness needs to work as:

  • An interactive command-line interface,
  • A headless / programmatic interface (CI, scripts, embedding in other agents), and
  • A web UI.

Critically, the backend must not be tied to any one of these UIs — the same core engine should be able to drive all three, so a UI is never load-bearing for the agent loop itself.

Requirements (as understood so far)

  • UI-agnostic core. One backend/engine; CLI, headless callers, and web UI are all clients of it, not separate implementations.
  • Multi-surface from the start, not retrofitted — several harnesses researched (Roo Code, early Cline) had to redo their architecture specifically because headless/CLI support was bolted onto an IDE-shaped core after the fact.
  • Informed by what already exists. Before locking in an architecture, understand what 20+ comparable systems do well, where they consistently fail, and what almost none of them do at all — see the survey below.

Requirements will get more specific once the open questions at the bottom of this page are answered — this section will be updated as decisions are made.

What the research says, distilled

Patterns worth adopting

  • One append-only event log as the decoupling substrate — every interface is a reader/writer of the same log, never calling another interface directly (OpenHands' EventStream, Claude Code's JSONL transcript).
  • A stable, language-agnostic headless interface with thin SDKs on top, rather than N separate implementations (Claude Code's claude -p, Cline's @cline/sdk).
  • Separate the reasoning plane from the execution plane — don't hard-wire where the model runs to where side effects happen (Devin's Outposts, GitHub Copilot's Actions-as-sandbox).
  • Layered, pluggable session persistence — start in-memory/file, graduate to a real store without changing the interface (LangGraph checkpointers, OpenAI Agents SDK sessions).
  • Permission enforcement lives in the core loop, not the UI — approval-state races and silently-ignored auto-approve flags are a recurring, cross-vendor bug class.
  • Multi-agent orchestration needs explicit state/control-flow, not free-form conversation — Microsoft moved AutoGen to maintenance mode for exactly this reason.

Recurring pain points across (nearly) every vendor

  • Context compaction silently breaking sessions — the single most common failure class in long-running agents.
  • Opaque token/cost accounting — a near-universal complaint, independent of pricing model.
  • "Rogue agent" incidents from missing hard sandboxing — Cursor's self-deletion, Windsurf's CVE, Replit's production-database deletion.
  • MCP servers are the most consistent unguarded edge of otherwise-sandboxed systems (even GitHub Copilot's firewall explicitly excludes them).
  • Vendor consolidation risk is real and recent — three surveyed tools exited independent existence during this research window alone.

What almost nobody does well — candidate differentiators

  • Real-time, legible cost/token accounting as a first-class UX surface.
  • Side-effect-aware checkpointing (filesystem and external state like a database, not just conversation history).
  • Governance/policy control over MCP servers.
  • A harness natively decoupled from day one, rather than retrofitted after the fact.
  • A meta-harness that orchestrates other vendors' harnesses as subagents — see below.

Candidate USP: a "harness of harnesses"

Could lite-harness spin up other existing coding-agent harnesses — Claude Code, OpenCode, Codex CLI, Gemini CLI — as subagents, instead of only spawning homogeneous subagents of itself? Two follow-up research passes (full findings in acp-and-meta-harness.md):

  • The Agent Client Protocol (ACP) is a real, spreading standard for client↔agent communication (native in Gemini CLI, Goose, OpenCode, GitHub Copilot CLI; Claude Code and Codex CLI reachable via Zed-maintained adapters). It has a rich session model, but it is strictly 1:1 — no parent/child delegation, no task routing, no result-merging, no propagation of permission decisions across nested agents. It's a good transport, not an orchestration layer.
  • This pattern already has prior art, and it's scrappy: 2026-vintage open-source projects (Bernstein, majiayu000/harness, claw-orchestrator, sage, Zen MCP's clink, ruvnet/metaharness, Parallel Code) already spawn multiple vendor CLIs as subprocess workers under one orchestrator — mostly via raw stdio wrapping. No major vendor supports spawning a different vendor's CLI as a subagent themselves.
  • The one problem nobody has solved cleanly: a unified permission model and a single legible cost ledger across heterogeneous underlying agents. That's the real whitespace, not the orchestration mechanics.

Status: candidate differentiator, not a committed decision.

Design principles carried forward

  1. One core agent loop, expressed as a reader/writer of a single append-only event log.
  2. Ship a stable, versioned headless protocol first; CLI, SDK, and web backend are three clients of it.
  3. Decouple where the model reasons from where tools execute.
  4. Design session/state persistence as a pluggable backend behind one interface.
  5. Treat permission enforcement as a property of the core loop, not the UI.
  6. Make irreversible/destructive actions require a structural gate, not a prompted one.
  7. Prefer explicit, typed multi-agent state/control-flow over free-form conversation.
  8. Build cost/token accounting and tracing in from the start, as a non-invasive side channel.
  9. Design tool primitives for the model's failure modes, not by wrapping raw OS primitives.
  10. Treat MCP governance as a first-class concern, not an afterthought.

Decisions made so far

None yet. The team has completed the research phase and agreed on the design principles above as inputs. No decisions have been made on language/runtime, deployment model, multi-agent scope, or provider strategy — see open questions below.

Open questions before the design phase starts

  • Target primary language/runtime for the core engine (TypeScript/Node, Python, Rust, Go)?
  • Local-first vs. cloud-hosted-first vs. both from day one?
  • Single-agent to start, or multi-agent (supervisor/subagent) as a v1 requirement?
  • Which model providers must be supported at launch — Anthropic-only, or provider-agnostic BYO-key from day one?
  • Which 1–2 differentiator candidates should lite-harness actually lead with?
